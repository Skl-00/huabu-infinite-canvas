# 插件 Durable Generation 续作反方审查

## 审查结论

本轮范围可以实施，但必须把“可见来源”与“执行事实”分开处理，并把串行约束落实在 runner，而不是只在测试里延迟请求。

## 反方意见与处理

### 1. 来源显示可能泄露秘密

任务来源只能使用 `pluginId`、插件节点类型、项目 ID 和目标节点 ID。不得把插件脚本、API Key、完整请求配置或远程结果 URL 拼入文案。

### 2. 串行化可能破坏部分成功

串行执行不能把多个槽位合并成一个请求，也不能因为前一个槽位失败就停止后续槽位。每个槽位仍须写入自己的成功或失败状态，最终状态继续由所有槽位推导。

### 3. 刷新验收可能被内存状态误导

图片和音频测试必须在刷新后重新读取任务仓储或通过任务中心展示结果，并断言 Provider POST 次数没有增加。仅检查 React 节点内容不足以证明 durable 复用。

### 4. 插件返回值可能是假媒体

图片测试使用可解码的 PNG；音频测试使用 `Blob` 响应并断言本地 `storageKey`。不能把任意文本或 HTML 响应当作媒体成功。

### 5. 现有全量测试已经通过

本轮修改应保持工作树已有改动，不回滚无关文件；验证必须重新运行，不能把历史 `52/52` 直接作为当前最终证据。

### 6. 任务中心 retry 可能丢失插件归属

如果 retry runner 只复制提示词、模型和参考素材，不复制 `request.canvas`，插件失败后的子任务会退化为独立任务，来源页面和插件身份都会丢失。四类 runner 必须统一继承原始上下文，不能只修复被测试到的一类。

## 通过条件

- 类型检查、生产构建、全量 Playwright 和差异检查均通过；
- 插件图片、音频和任务来源专项证据均通过；
- 至少一条插件失败后从任务中心重试的浏览器测试证明上下文未丢失；
- 进度文件明确区分本轮新增证据与仍未验证的边界。
