# 画布参考资源真实执行链对抗审查

## 主要反方问题

### 1. 只有 storageKey、没有 content 的图片

如果只把 `resourceKind` 改成检查 `storageKey`，但 `readReferenceImage` 仍把空字符串放入 `dataUrl`，Provider 会收到空图片。必须在执行前从本地 Blob hydrate 成 data URL，并在读取不到 Blob 时明确失败，不能静默继续。

### 2. content 是 blob URL、data URL 或远程 URL

`storageKey` 不是唯一输入形态。已经持久化的图片应优先使用本地 Blob；未持久化但仍可读取的 `data:`、`blob:` 或远程地址应保留。远程 URL 需要沿用现有图片读取/代理策略，不能把展示地址误当成 Provider 一定可访问的地址。

### 3. 连接路径被错误覆盖

当前语义是 Config 输入优先于直接输入，Group 需要展开；修复不能把多个路径简单拼接造成意外重复，也不能因存在无效 Config 输入而遮蔽有效直接输入。最终必须按资源节点 ID 稳定去重。

### 4. 多模态文本与图像编辑分叉

文本请求使用 `image_url`，图像编辑使用 multipart，视频适配器可能使用 data URL 或文件。若只修一条 API 路径，用户仍会遇到“某个节点能用、另一个不能用”。上下文编译和 hydrate 必须成为公共前置步骤。

### 5. 刷新、恢复、删除和断线

刷新后节点展示 URL 可能尚未恢复；删除或断线后旧的 React 引用不能污染下一次执行。测试必须重新读取当前 nodes/connections，而不是复用旧上下文。

### 6. 参考栏与执行状态不一致

参考栏应使用同样的资源有效性规则。若缩略图暂时不可展示但 storageKey 存在，可以显示占位并保留可执行状态；若本地 Blob 已丢失，提交前必须报告“参考素材不可读取”，不能假装发送成功。

### 7. 上限、顺序和重复连接

Provider 能力限制由现有 capability 层负责；本轮不静默截断参考。输入顺序应按连接图稳定顺序，重复连接只保留一次，避免请求结果因 React 渲染顺序变化而漂移。

## 审查结论

可实施，但不能只改一个条件表达式。最小可靠改动是：统一资源存在性、执行前统一媒体 hydrate、公共上下文去重、参考栏使用持久化键恢复展示，并用请求体断言覆盖真实链路。
