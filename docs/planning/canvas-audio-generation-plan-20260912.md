# 画布音频持久生成计划

## 目标

将画布音频生成从“请求完成后直接写节点”迁移到独立的 `AudioRun` 持久任务仓储，使其具备提交前落盘、跨刷新可识别、结果媒体可恢复、节点删除后任务仍保留和失败可重试的能力，并与已经验证的图片/视频任务边界保持一致。

## 本阶段范围

- 新增 `AudioRun` 类型、localforage 仓储、广播刷新和 Web Locks 互斥。
- 新增 `startAudioRun`、`retryAudioRun`、`resumeAudioRun` 和重新保存能力。
- 画布音频新建、重试和空音频节点生成全部复用 `AudioRun`。
- 画布打开后按 `generationRunId` 将音频结果重新投影到仍存在的节点。
- 音频任务上下文只保存项目、场景、目标节点和来源节点 ID。
- 结果先写入 `media_files`，再写入任务记录，最后回填节点。
- 迁移音频结果的媒体清理保护，避免任务仍引用的音频被清除。
- 增加提交、失败、刷新恢复、节点删除、场景复制和凭据脱敏测试。

## 明确不纳入

- 不把文本流式回答伪装成可恢复的音频或通用任务。
- 不在本阶段重写插件协议；插件音频继续由插件脚本负责。
- 不引入批量音频并发；免费渠道保持单请求串行。
- 不改变现有音频模型配置字段和 Provider 协议。
- 不删除历史节点上已有的直接媒体内容。

## 设计约束

- 任务创建和 `running` 状态必须在 Provider 请求之前持久化。
- 页面关闭或跨标签失去执行权时标记 `interrupted`，不得自动重复提交。
- API Key 只从当前配置解析，不进入任务记录、错误文本、日志或测试快照。
- `AudioRun` 只保留必要的配置快照、渠道指纹和音频结果引用。
- 任务记录成功但节点回填失败时，任务仍须保持成功，结果留在任务仓储中。
- 同一页面和第二标签不得对同一任务重复发起 Provider 请求。
- 场景复制清理生成任务身份，保留已生成媒体内容。

## 实施顺序

1. 复用现有音频 API 与媒体存储，定义 `AudioRun` 数据模型和仓储。
2. 实现提交、保存、失败、刷新中断和重试边界。
3. 将画布音频新建和音频节点重试切换到 `startAudioRun`。
4. 接入结果投影、任务引用保护和场景复制清理。
5. 增加定向 Playwright 测试，再跑完整回归、类型检查、构建和差异审计。

## 反方审查

- Blob 本身不能作为任务事实；必须保存状态、请求快照、结果引用和错误边界。
- `requestAudioGeneration` 返回成功但媒体保存失败时，不能重新请求 Provider；应保留可重新保存的中间状态。
- 插件脚本可能一次性返回音频且没有远端续查协议，刷新后只能标记未知，不得猜测成功。
- 音频结果可能没有可读 duration，节点仍应保存媒体和 MIME，不因元数据读取失败丢弃结果。
- 旧节点没有 `generationRunId` 时继续保留当前人工重试路径，避免历史数据失效。
- 任务仓储引用的 `audio:*` 媒体必须纳入清理保护，否则刷新后任务会变成空结果。

## 验收标准

- 音频 Provider 请求前已有可读取的任务记录。
- 明确失败不重试 Provider，重试创建新的子任务。
- 刷新和第二标签不会重复提交。
- 成功音频结果可在任务记录和节点中恢复。
- 节点删除后音频任务和媒体仍保留。
- 复制场景不复制运行身份。
- Web 类型检查、音频定向测试、全量回归和生产构建通过。
