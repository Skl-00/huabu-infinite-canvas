# 插件 Durable Generation 边界验收反方审查

## 审查结论

本计划可以实施，但必须把“插件 UI 回调”与“任务仓储事实”分开验证。任何一个节点是否仍然存在，都不能决定任务状态是否被保存；同时不能用内存中的旧 React 树代替刷新后的 durable 证据。

## 主要反例

### 1. 图片部分成功被插件层误报为失败

插件 API 返回的是成功图片数组，runner 内部还可能存在失败槽位。测试必须直接读取 image run 的槽位状态，不能只看插件 metadata 或第一张图片。

### 2. Abort 后文本被自动重跑

插件卸载或请求取消可能触发第二次 effect。测试要统计 Provider POST 次数，并在刷新后再次断言中断记录仍在，不产生隐式新任务。

### 3. 删除节点后的异步回写污染其他节点

删除目标后，如果实现按位置或旧数组索引回写，后续节点可能被写入结果。测试必须删除目标、创建一个新节点，再等待原请求完成并断言新节点没有旧任务内容。

### 4. 复制副本仍带旧运行身份

仅比较节点数量不足以证明隔离。需要比较原节点与副本节点 ID、generationRunId、generationRunKind，以及复制后 Provider POST 数量。

### 5. 失败/中断错误泄露秘密

Provider 错误可能包含 Authorization 或脚本异常正文。新增测试要对完整 run JSON 做秘密和脚本指纹断言，且来源展示只使用安全标识。

### 6. 仅专项测试通过不代表现有行为未回归

新增边界测试后必须重新运行 `typecheck`、`build` 和完整 Playwright。构建与 Playwright 不能并行，避免争用 `.next`。

## 必须的修复闸门

- 若测试发现删除节点后任务状态无法落库，先修 runner 持久化，不用测试绕开问题。
- 若 Abort 进入 `failed` 而不是 `interrupted`，先确认是浏览器取消、Provider 明确失败还是未知提交状态，再修状态映射。
- 若复制逻辑清除了任务 ID 但插件重新挂载仍自动提交，修复插件的 durable 复用判定，而不是增加测试等待。
- 若发现任务存储含秘密，必须清除写入路径并补字段级审计。

## 通过条件

- 边界专项测试全部通过；
- 类型检查、构建和全量 Playwright 通过；
- `git diff --check` 通过；
- 进度文档准确区分已验证事实和仍未验证的真实 Provider/云同步边界。
